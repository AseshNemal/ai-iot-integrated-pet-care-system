2. Methodology

This was a static, read-only source-code assessment of the entire repository (backend/, frontend/, Pet Health Tracker/, and root configuration). No application code, configuration, dependencies, or Git history were modified, and no live/production systems, third-party services, or deployed endpoints were attacked or queried.

Steps performed

  1. Enumerated the full repository structure and identified every route file, model, middleware, config file, and frontend component.
  2. Read every backend route handler (backend/src/API/routes/*.js), model (backend/src/API/model/*.js), middleware, and the Express app bootstrap (backend/src/app.js) in full.
  3. Grepped the codebase for security-relevant patterns: req.body, findByIdAndUpdate, deleteMany, jwt, password, bcrypt, dangerouslySetInnerHTML, eval, multer, express.static, console.log, process.env, CORS, and others.
  4. Inspected environment/config handling, and confirmed via git status / git log --all --full-history which credential-bearing files are tracked in version control (values were never printed — only key names, lengths, and structural "does this look like a placeholder" checks were performed).
  5. Reviewed the React frontend for XSS sinks, client-side trust boundaries, session/localStorage usage, and the payment/checkout flow.
  6. Reviewed the IoT chain: the Cloudflare Worker (Pet Health Tracker/worker(cloudflare).js), the Firebase Realtime Database/Firestore integration, and the client-side telemetry dashboard.
  7. Ran npm audit --package-lock-only against both backend/package-lock.json and frontend/package-lock.json (lockfile-only; no packages were installed or modified) to catalogue known-CVE dependency risk separately from application-code risk.
Constraints honoured throughout: no code/config edits, no credential rotation, no authentication/authorization changes, no dependency updates, no commits, no pushes, no destructive testing, no attacks against third-party systems, and no secret values were ever printed or recorded — only key names, presence, and structural characteristics.

V01 — Sensitive Credentials Committed to Source Control

Critical
Status: Verified from sourceOWASP A02:2021, A05:2021CWE-798, CWE-312
Affected files backend/.env.production (tracked), backend/src/utils/firebase-service-account.json (tracked) Affected code Both files are plain-text credential files committed at the repository root/utils directory. Confirmed via git ls-files and git log --all --full-history. Evidence
  • backend/.env.production is present in git ls-files output and contains real-looking (non-placeholder) values for MONGODB_URL (a mongodb+srv:// Atlas connection string with embedded credentials), GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET (prefixed GOCSPX-, Google's real client-secret format), GEMINI_API_KEY (prefixed AIzaSy, Google's real API-key format), and SESSION_SECRET (low-entropy, human-chosen looking). No secret values are reproduced in this report.
  • backend/src/utils/firebase-service-account.json is a Firebase Admin SDK service-account key — it contains the standard Admin SDK fields (type, project_id, private_key_id, private_key — 1704 characters, consistent with a real RSA private key — client_email, client_x509_cert_url, etc.). This is a genuine server-side secret, not the public Firebase Web SDK config.
  • The repository's own .gitignore (added in commit c3e780a) attempts to exclude both files going forward, but gitignore does not retroactively untrack already-committed files — both remain tracked and are readable in the full clone/history from the initial commit onward.
  • The commit message for c3e780a explicitly states: "This commit does not remove or modify the currently tracked backend/.env.production or firebase-service-account.json… That cleanup (secret rotation, untracking the real credential files, and rewriting Git history to purge them) is a separate follow-up step." — first-party confirmation from the project owner.
Root cause Real production credentials were created directly inside the repository working tree and committed before any .gitignore exclusion existed; adding the ignore rule afterwards does not remove history. Attack scenario Anyone with collaborator/clone access to the repository (the repository is confirmed private — see §1.1) can check out any historical commit and obtain the committed credentials. The privilege each credential actually grants differs and is stated precisely rather than lumped together: the MongoDB connection string grants direct database read/write per the permissions of the embedded database user; the Firebase Admin private key grants unrestricted server-side read/write to the project's Firestore and Realtime Database, bypassing all client-facing Firestore security rules (Admin SDK credentials are explicitly designed to bypass those rules); the Google OAuth client secret allows an attacker to impersonate this application to Google's OAuth token endpoint (e.g. exchanging an intercepted authorization code for tokens) — it does not by itself grant access to arbitrary Google user accounts or to Google's infrastructure; the Gemini API key allows billed API usage at the project owner's expense; the session secret compounds with V10 to enable forged session cookies. Impact Confidentiality and integrity (full database read/write via the MongoDB credential; full Firestore/Realtime Database read/write, bypassing security rules, via the Firebase Admin key), cost abuse (Gemini key), and — specific to the OAuth client secret only — potential impersonation of the application itself in the OAuth flow (not direct compromise of end-user Google accounts). OWASP classification A02:2021 – Cryptographic Failures (secrets exposure); A05:2021 – Security Misconfiguration CWE CWE-798 (Use of Hard-coded Credentials), CWE-312 (Cleartext Storage of Sensitive Information) Severity: Critical — The Firebase Admin key and MongoDB credential alone are sufficient for direct, unmediated, rule-bypassing access to the production database and data stores; severity does not rely on the OAuth-secret claim. Safe demonstration method Show git ls-files | grep -E "env|firebase-service-account" and git log --all -- backend/.env.production to prove tracked status, without ever printing the file contents. Screenshot the redacted KEY=<REDACTED> listing used in this assessment. Potential remediation (not yet implemented) Rotate every exposed credential (MongoDB user, Google OAuth client, Gemini key, Firebase service account, session secret); remove both files from all Git history (e.g. git filter-repo); keep only the already-tracked .example templates; load real values exclusively from an untracked .env or a secrets manager. Distinctness Distinct root cause — the only finding about credential handling in version control itself, separate from V10 (hardcoded fallback secret in application code) and V24 (secret disclosed via API response).

V02 — Broken Access Control Across Privileged API Routes

Critical
Status: Remediated and verified 24 Sep 2026OWASP A01:2021CWE-862
Affected files employeeRoutes.js, medicalRecords.js, pets.js, productRoutes.js, orderRoutes.js, expenseRoutes.js, feedbackRoutes.js, PetAdRoutes.js (all /admin/* sub-routes), notificationRoutes.js (create routes), gemini.js Original affected code (pre-remediation) None of these route files import or apply the project's own authenticate middleware (backend/src/API/middleware/auth.middlewere.js). A repository-wide grep for authenticate shows it is used only inside appointmentRoutes.js and the base /user route. Original evidence
  • employeeRoutes.js: POST /create, GET /, GET /get, GET /count, DELETE /:id, PUT /:id, POST /appointment, DELETE /sorted-appointment-data (a raw deleteMany({})) — all reachable with no session/token.
  • medicalRecords.js: full CRUD on pet medical records, no auth on any route.
  • pets.js: add/list/update/delete/find-by-owner, no auth on any route.
  • productRoutes.js: add/update/delete/restock, no auth (covered further in V14/V19).
  • orderRoutes.js: GET /all returns every customer's orders, no auth.
  • expenseRoutes.js: full CRUD on internal company expenses, no auth.
  • feedbackRoutes.js: create/delete/edit any feedback, no auth.
  • PetAdRoutes.js: /admin/list, /admin/approve/:id, /admin/reject/:id, /admin/delete/:id, /admin/approved/delete/:id, /admin/approved/edit/:id — every admin moderation action for the pet-adoption feature has zero authentication or role check, despite being explicitly named "Admin:" in code comments.
  • notificationRoutes.js: POST /appointment and POST /appointment-booking (notification creation) have no auth check at all.
  • gemini.js: both AI endpoints are open (see V17).
Root cause The authenticate middleware exists and works correctly where it is applied, but was never wired into the vast majority of state-changing and data-listing routes — a systemic omission rather than a bug in the middleware itself. Attack scenario An anonymous caller can, in a single crafted request each: create an "employee" record with role: "Admin"; delete any employee, pet, medical record, product, order, expense, or feedback entry by ID; wipe the entire AppointmentData collection; and approve, reject, or permanently delete any pet-adoption ad. No login of any kind is required for any of this. Impact Data manipulation, data destruction, privilege escalation (self-created admin-role employee), privacy exposure (all customers'/patients' records), financial-data exposure (expenses). OWASP classification A01:2021 – Broken Access Control CWE CWE-862 (Missing Authorization) Severity: Critical — Unauthenticated full CRUD (including delete) on nearly every business entity in the system, plus the ability to self-provision a privileged "employee" identity. Safe demonstration method From a local instance, issue unauthenticated curl requests (e.g. POST /employee/create with role: "Admin", then GET /employee) against localhost:8090 only — no external target. Remediation implemented
  • Applied authenticate before every V02-affected privileged handler in employeeRoutes.js, medicalRecords.js, pets.js, productRoutes.js, orderRoutes.js, expenseRoutes.js, feedbackRoutes.js, notificationRoutes.js, and gemini.js.
  • Added authorizeRoles and required both authentication and the Admin role on all six PetAd /admin/* routes.
  • Added a constrained role field to user.model.js, defaulting all ordinary and legacy users without an assigned role to User. Administrative access must be provisioned through a trusted database/administration process; no public role-elevation endpoint was added.
  • Enabled Axios credential forwarding in frontend/src/index.js and added server-side employee/admin session creation and logout, so both Google/Passport and employee authentication flows work on protected routes.
Post-remediation verification Unauthenticated live requests to representative endpoints in every affected module returned HTTP 401 before reaching a data handler. An authenticated non-admin identity returned HTTP 403 from the PetAd role guard, while an Admin identity passed the guard. Static route assertions confirmed that authentication is the first handler on every protected route, all affected routers loaded successfully, the backend started normally, and the frontend production build completed.
Result: V02 is remediated. The separate V03 object-level authorization issue and V04 fail-open notification issue were intentionally not changed and remain open.
Distinctness One consolidated root cause (per the assignment's anti-duplication rule) covering ~10 route files that all suffer from the identical "no authentication middleware applied" problem — intentionally not split into one finding per route/collection. Distinct from V03/V04 (authentication present but authorization logic itself is broken) and V20 (identity spoofing even where some check exists).

V03 — IDOR on Appointment Endpoints Despite Authentication

High
Status: Verified from sourceOWASP A01:2021CWE-639
Affected files backend/src/API/routes/appointmentRoutes.js Affected code GET /user/:userId (line 104), PUT /:id (line 117), DELETE /:id (line 146), GET /all (line 197, explicitly commented "without authentication"). Evidence 
router.get("/user/:userId", authenticate, async (req, res) => {
  const { userId } = req.params;
  const appointments = await Appointment.find({
    $or: [{ petOwnerId: userId }, { employeeId: userId }]

The authenticate middleware only confirms a valid session exists — it never compares the session's user to the :userId/:id in the URL. The same pattern repeats on PUT /:id and DELETE /:id, and GET /all has no authentication gate at all. Root cause Object-level authorization (does this authenticated user own this resource?) was never implemented — only authentication (is this a logged-in user at all?) was. Attack scenario Any logged-in customer can substitute another customer's or employee's ID in the URL to read, edit (including reassigning employeeId/petOwnerId via V05), or delete that person's appointments. Impact Privacy exposure (pet owner names, appointment details), data manipulation, data destruction, cross-account access. OWASP classification A01:2021 – Broken Access Control CWE CWE-639 (Authorization Bypass Through User-Controlled Key) Severity: High — Requires only a normal authenticated session (any customer account), not a privileged one, to access or destroy other users' data. Safe demonstration method Register two local test accounts, log in as account A, and request account B's /api/appointments/user/:B_id. Potential remediation Compare req.user._id to the resource's owner field (or the requested :userId) before returning/mutating data; scope queries to req.user._id rather than a client-supplied ID. Distinctness Distinct from V02 (there, authentication is entirely absent; here it is present but object-level authorization is missing) and from V04 (a different, fail-open mechanism on a different router).

V04 — Fail-Open Authorization on Notification Endpoints

High
Status: Verified from sourceOWASP A01:2021CWE-863
Affected files backend/src/API/routes/notificationRoutes.js Affected code Lines 14, 41, 61, 110. Evidence 
// Check if the authenticated user is requesting their own notifications
if (req.user && req.user._id.toString() !== userId.toString()) {
  return res.status(403).json({ error: 'Unauthorized access to notifications' });
}
This router never applies the authenticate middleware, so req.user is only populated if a valid session cookie happens to be present — it is never required. When a request arrives with no session at all, req.user is undefined, the condition short-circuits to false, and the ownership check is silently skipped — the request proceeds and returns the target user's notifications. Root cause The ownership check was written as a conditional ("if a user is attached, verify ownership") instead of a mandatory gate ("require a user, then verify ownership") — a classic fail-open logic error, distinct from simply forgetting the check (V02) or forgetting to scope by owner (V03). Attack scenario An unauthenticated request to GET /api/notifications/user/:anyUserId, PUT /:notificationId/mark-read, or PUT /user/:userId/mark-all-read succeeds for any target user ID, with no credentials at all. Impact Privacy exposure (notification content, which includes pet names, appointment times, and staff names), unauthorized state changes (marking another user's notifications read). OWASP classification A01:2021 – Broken Access Control CWE CWE-863 (Incorrect Authorization) Severity: High — Fully unauthenticated data access, worse than V03 because no session is needed at all. Safe demonstration method Send an unauthenticated curl request to the local instance's notification endpoints with an arbitrary Mongo ObjectId. Potential remediation Apply the authenticate middleware to this router and make the ownership check unconditional (reject when req.user is absent, not only when it mismatches). Distinctness Distinct mechanism from V02 (no auth attempted at all) and V03 (auth present, ownership check simply missing) — here auth is optional and the ownership check exists but is bypassable by omitting credentials entirely.

V09 — Client-Side-Only Employee Authorization via Unsigned localStorage

Medium
Status: Verified from sourceOWASP A07:2021CWE-602
Affected files frontend/src/components/EmployeeLogin.js, frontend/src/components/EmployeeDashboard.js Affected code EmployeeLogin.js line 25: localStorage.setItem("employeeData", JSON.stringify(response.data.user)). Evidence The employee "session" after login is nothing more than the JSON the server returned, stored verbatim and unsigned in localStorage. V24 — Session ID Disclosed in API Response Body

Low
Status: Verified from sourceOWASP A01:2021CWE-200
Affected files backend/src/app.js Affected code 
app.get("/get-session", (req, res) => {
  if (req.user) {
    res.json({ sessionID: req.sessionID, user: req.user });   // raw session ID in response body
  } ...
});
This endpoint is called from at least ten frontend components (profile.js, Header.js, PaymentPage.js, Notifications.js, etc.) as the app's primary "who am I" check. Root cause The session cookie itself is correctly marked httpOnly (not readable by JavaScript), but this endpoint unnecessarily hands the raw req.sessionID back to any script running on the page via a normal JSON response — an unneeded exposure of an internal identifier that has no legitimate use on the client (the frontend only ever needs the user field to determine login state). Attack scenario Correction from an earlier draft: this finding previously claimed a script-execution vector could use the exposed sessionID to directly hijack the session, "without needing to bypass httpOnly". The exposure becomes meaningfully dangerous only if combined with knowledge of SESSION_SECRET (to re-sign the ID) — which is precisely the condition V10 and V01 separately document — or if the session store itself can be queried directly by ID through some other channel not evidenced in this codebase. Impact Unnecessary exposure of an internal session identifier (a hygiene/information-disclosure issue on its own). It becomes a genuine hijacking enabler only in combination with V10/V01 (an attacker who can re-derive or already knows SESSION_SECRET) — it is not, by itself, a session-hijacking or httpOnly-bypass vulnerability. OWASP classification A01:2021 – Broken Access Control (session management) CWE CWE-200 (Exposure of Sensitive Information to an Unauthorized Actor) Severity: Low — Unnecessary information exposure with no demonstrated standalone exploit path; real risk is conditional on a separate secret-compromise finding (V10/V01). Safe demonstration method While authenticated locally, call GET /get-session from the browser console and observe sessionID in the JSON response. Potential remediation Remove sessionID from this response entirely; the frontend only needs user to determine login state. Distinctness Distinct from V25 (this is an API-response exposure channel, not a server-log exposure channel).

11. Secure Development Best Practices for Remediation

  • Authentication & authorization: apply the existing authenticate middleware consistently; add object-level ownership checks; move to a role-aware authorization model rather than trusting client-supplied identity fields.
  • Credential handling: hash all passwords with bcrypt (already a dependency); rotate and remove all committed secrets; load configuration exclusively from untracked environment files or a secrets manager; fail fast on missing required secrets rather than falling back to a default.
  • Input validation & output encoding: validate and whitelist fields on every write endpoint (defeats mass assignment); sanitize any HTML rendered via dangerouslySetInnerHTML (e.g. with DOMPurify), or avoid the raw-HTML sink entirely.
  • Server-side business logic: recompute prices/totals and validate quantities server-side; never trust client-supplied monetary or inventory values.
  • Network egress control: allowlist destinations for any server-initiated outbound request (image proxy); block requests to private/loopback/link-local ranges.
  • File uploads: enforce MIME/extension allowlists and size limits; generate server-side filenames; isolate upload storage from the application origin or serve with restrictive headers.
  • Defense in depth: add Helmet-based security headers, CSRF protection on session-authenticated state changes, and rate limiting across authentication and resource-intensive endpoints.
  • Logging hygiene: remove sensitive data (session IDs, credentials, full user objects) from logs and client-facing error responses.
  • Dependency management: establish a routine npm audit / update cadence, prioritizing direct dependencies with application-relevant advisories.
  • IoT/device trust: require per-device authentication (API key or signed payload) for telemetry ingestion; validate payload schema and value ranges before persisting.

12. Conclusion

29 security findings/candidates (V01–V29, including one consolidated dependency-risk category) were identified during this static, read-only assessment, spanning credential management, access control, authentication, business logic, injection/XSS, SSRF, file handling, and IoT device trust — plus a separately-tracked dependency-vulnerability inventory (37 backend, 210 frontend advisories via npm audit, most concentrated in a handful of shared transitive packages). This deliberately avoids asserting that all 29 are conclusively distinct, exploitable vulnerabilities; each carries its own status, and the three are not interchangeable:

  • Verified from source (25 of 29): V01, V02, V03, V04, V05, V06, V07, V08, V09, V10, V11, V13, V14, V15, V17, V18, V19, V20, V21, V22, V24, V25, V26, V27, V29 — the vulnerable code path is directly evidenced in the repository.
  • Partially verified — sink/root cause confirmed from source, but the full exploit chain or live-deployment exposure requires runtime confirmation (2 of 29): V16 (the unsanitized dangerouslySetInnerHTML sink is verified; whether Gemini output can reliably be steered to contain executable markup was not demonstrated end-to-end) and V28 (the IoT ingestion pipeline's lack of authentication is verified in source; whether the Cloudflare Worker is currently deployed and reachable was not confirmed).
  • Strong candidate — requires runtime confirmation (2 of 29): V12 (CSRF exploitability against the live session/cookie configuration) and V23 (OAuth state-parameter weakness under the live Passport/session interaction).

All 32 vulnerability candidates supplied at the start of this engagement were individually checked against the current codebase (see §2's checklist), with two additional findings (V08, V09) surfaced during review. Several findings from an earlier draft of this report were corrected after review: the repository-visibility claim, the OAuth-secret impact framing (V01), the V13 SSRF demonstration and severity, the V14 path-traversal claim, the V19 stock-depletion claim, the V20 scope, and the V24 session-ID/httpOnly claim were each revised to match only what the source code actually supports.
